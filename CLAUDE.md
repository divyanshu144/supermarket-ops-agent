# CLAUDE.md — Supermarket Ops Agent

Standing operating manual for this repo. Applies to every session. Derived from
`claude_onboarding.md`; that file is the source, this is the tailored version. If the two
ever disagree, `claude_onboarding.md` wins and this file gets corrected.

---

## 1. The project

A conversational agent that runs a small Indian kirana / supermarket store end-to-end.
**Telegram is the only interface.** No web app, no admin panel, no forms — the chat is the
product. The owner receives stock, cuts bills, checks stock, runs customer credit, closes the
day, and pulls invoices and analysis decks, all in plain terse English.

Source brief: `Assignment.md` (BigMantra take-home). Read it before any design work.

### The one thing that decides pass/fail

**This is agent-first.** The model orchestrates; we author skills and tools and let it decide
what to call. The brief states that a regex / keyword intent router doing the real work is an
**automatic fail**, and that a LangGraph-style node-per-command state machine misreads the task.

> If you find yourself writing a large if/elif intent router full of regexes, you've taken the
> wrong turn.

Corollary: clarifying questions (`add atta` → "Which one — Aashirvaad 5kg or loose?") must come
from the **model**, never from a hardcoded branch.

### Capabilities the owner must have

Receive stock · add a product · cut a multi-item bill · edit a bill mid-build · stock queries ·
low-stock/reorder · khata put/pay/balance · daily close · PDF GST invoice · PPTX analysis deck
with real charts · standing preferences that survive `/new`.

### Deliverables

- A **live bot** kept running through the review window, `@handle` in the README.
- The **skills & tools surface** — explicitly "the heart of what we grade".
- **PDF invoices** and a **PPTX analysis deck with real charts**, generated by the agent's own
  tools (not screenshots, not plain text).
- **README (~1 page)**: harness choice and why, how the control loop works, skill/tool design,
  and how each hard part was solved.
- **4–5 min recording**: receive stock → multi-item bill with an edit → oversell guard → khata
  cycle → PDF invoice → analysis deck → set a preference, `/new` chat, show it's remembered.

## 2. Stack — locked decisions

Locked on 2026-07-29. Do not relitigate without saying so explicitly; record any change in
`tasks/agent_memory.md` under Architecture Decisions.

| Layer | Choice | Why |
|---|---|---|
| Harness | **Claude Agent SDK (TypeScript)** | Listed first in the brief. Skills, tool schemas, subagents and sessions are first-class, so the graded surface is the SDK's own idiom rather than scaffolding we invent. |
| Runtime | Node 24 + pnpm | Installed locally (Node v24.13.0, pnpm 9.15.4). |
| Telegram | grammY | Typed, middleware-based, long-poll for dev and webhook for prod. |
| Database | **Postgres** | Row-level locking and real transaction isolation — the honest answer to the concurrency and atomic-decrement requirements. |
| DB access | Drizzle ORM + drizzle-kit migrations | Typed schema, SQL-first, migrations in-repo. |
| Validation | Zod | Tool input schemas double as runtime validation at the trust boundary. |
| PDF | pdfmake | Declarative documents with native table support — a GST invoice is two tables. No headless Chrome, so no heavyweight container or cold-start risk. |
| PPTX | pptxgenjs | Emits **native** PowerPoint charts — the brief demands real charts, not images. |
| Model | `claude-opus-5`, adaptive thinking | Tool-orchestration reliability outweighs token cost. No cheaper routing without an explicit decision. |
| Telegram transport | grammY, long-polling in dev **and** prod | No public URL, webhook config or TLS. Redelivery dedupe is required regardless of transport. |
| Tenancy | One store per Telegram chat | Reviewers run the same script concurrently; a shared store lets one reviewer's stock-in silently defeat another's oversell-guard demo. |
| Tests | Vitest | Fast, TS-native, works for unit and integration. |
| Lint / format | ESLint + Prettier | |
| Deployment | Railway | Managed Postgres attached in one click, push-to-deploy, stays running through the review window. |

All stack decisions are now made. The design spec is
`docs/specs/2026-07-29-supermarket-ops-agent-design.md` — read it before implementing anything.

## 4. Architecture map

Proposed shape — refine it in `docs/specs/`, then update this map to match reality. It is a
map, not a wish: when the code moves, this section moves with it.

```
Telegram ──> adapter ──> agent runtime ──> tools ──> Postgres
 (grammY)   (dedupe,    (Claude Agent      (thin,    (invariants
             session)     SDK loop)       validated)   enforced)
                              │
                              └──> skills (.claude/skills/) tell the model
                                   how to run the store
```

```
src/
  telegram/      grammY adapter: update dedupe, chat→session mapping, typing indicators,
                 file delivery (PDF/PPTX back to chat)
  agent/         Claude Agent SDK setup: system prompt, skill loading, subagents,
                 session resume, the observe→reason→act loop
  tools/         in-process SDK MCP tools, Zod-schema'd. Thin. Each one enforces its own
                 invariants and returns structured results the model can reason over
    inventory.ts   receive stock, add product, stock levels, reorder report
    billing.ts     open/amend/finalize a bill, tax computation, oversell guard
    khata.ts       credit ledger: charge, settle, balance, statement
    analytics.ts   daily close, sales aggregates, stock health, GST collected
    documents.ts   invoice PDF, analysis PPTX
    memory.ts      read/write owner preferences
  domain/        pure business logic — GST slabs, CGST/SGST split, rounding, unit
                 conversion, pricing rules. No I/O, exhaustively unit-tested
  db/            Drizzle schema, migrations, transaction helpers, repositories
    repositories/access.ts   invite codes: create, atomic redeem, revoke, hasStore
    repositories/usage.ts    per-store daily spend and cumulative session cost
  telegram/gate.ts          access gate: only chats that own a store reach the agent
  telegram/rate-limit.ts    per-chat sliding-window rate limiter (in memory)
  agent/limits.ts           per-run turn, budget and time limits
  config/        env parsing and validation (fail fast at boot)
.claude/skills/  the capability surface the model reads: inventory, billing, khata,
                 analytics, documents
docs/specs/      written specs      docs/plans/  implementation plans
tasks/           todo · lessons · agent_memory
```

**Entry point:** `src/index.ts` — validate config, run migrations check, wire the Telegram
adapter to the agent runtime, start.

### Layering rule

`domain/` knows nothing about the DB or the agent. `tools/` compose `domain/` + `db/`.
`agent/` knows about tools but not about Telegram. `telegram/` knows about the agent but never
about the DB. Dependencies point one way. Business rules never live in the system prompt.

## 5. Domain invariants

These are the graded "hard parts". Each is enforced **where the data changes** — in a tool or a
DB constraint — never hoped for in a prompt. Every one of these needs a test that proves it.

| Invariant | Enforcement |
|---|---|
| **Grounding** | Prices, GST slabs and stock come from the DB via tools. The agent never invents a product or price. Unknown SKU → tool returns a miss, model asks. |
| **Oversell guard** | Stock cannot go negative. Billing 10 when 6 exist is refused **at the tool layer**, with a DB `CHECK (quantity >= 0)` as the backstop. |
| **GST correctness** | Per-item slab, intra-state CGST+SGST split, correct rounding, legible tax breakup on the bill. Each SKU carries an HSN code. 0% loose staples, 5% packaged staples, 12–18% FMCG. |
| **Multi-turn bills** | A bill accumulates across messages and supports edits. Stock decrements **only on finalize**, never on add-to-cart. |
| **Idempotency** | Telegram redelivers updates. Every mutating tool takes an idempotency key; a retried finalize must not double-bill or double-decrement. Enforced by a unique constraint, not by checking-then-writing. |
| **Concurrency** | Two bills, or a sale plus a stock-in, in flight together must not corrupt stock. Use `SELECT … FOR UPDATE` inside a transaction; never read-modify-write across statements. |
| **Guardrails** | Don't sell below cost, don't delete stock, don't settle a khata that doesn't exist. Confirm or refuse — the tool returns a refusal the model must relay, it does not silently comply. |
| **Memory** | Standing preferences (default payment mode, preferred brand, shop name/GSTIN) persist in Postgres, **outside the context window**. `/new` clears the conversation, not what the store knows. |
| **Real artifacts** | PDF invoice and PPTX deck are generated by the agent's own tools with real charts. |
| **Access** | Only chats that own a store reach the agent. Invite codes are single-use and redeemed atomically (`repositories/access.ts`, `telegram/gate.ts`). |
| **Spend** | Per-run turn, budget and time limits, a per-store daily budget and a per-chat rate limit (`agent/limits.ts`, `repositories/usage.ts`, `telegram/rate-limit.ts`). |

### Money and units

Store money in **integer paise**, never floats. Round only at the documented boundary and round
once. Loose vs packaged is a product attribute, not a naming convention. Units: kg/g/litre/ml/
packet/dozen/piece — conversions live in `domain/`, tested.

## 6. Operating rules (non-negotiable)

**Process skills first.** If a relevant skill exists, invoke it *before* acting.

- **New feature / "let's build X"** → `brainstorming` (discuss → spec) → `writing-plans`
  (step-by-step plan) → `subagent-driven-development` (fresh subagent per task, review between
  tasks) → `finishing-a-development-branch`.
  **No code until the spec *and* the plan are approved.**
- **Bug / failure** → `systematic-debugging`: Reproduce → Locate → Isolate → Fix → Verify.
  Never jump to a fix before isolating. Never mark it fixed before verifying.

**Plan mode default.** Anything 3+ steps or architectural: plan first, check in **before**
implementing, not during. If it goes sideways mid-task, **stop and re-plan** — don't improvise
forward.

**Subagents.** Offload research, codebase exploration and parallel analysis to subagents to keep
the main context clean. Main context is for decisions and writing code.

**Core principles.**
- *Simplicity First* — the smallest change that works.
- *No Laziness* — fix root causes. No workarounds, no debt, no papering over.
- *Minimal Impact* — touch only the files the task needs. No drive-by refactors.

**Git.** Never commit on `main` — branch first. Commit and push only when asked. Integrate via
`finishing-a-development-branch` (merge / PR).

**Writing.** The README carries our reasoning, not a model's. Write it in plain prose, first
person, concrete. Document edge cases we didn't handle rather than papering over them — the
brief explicitly rewards that.

## 7. Verification before done

Never claim done without proof. Run the gate and show the output:

```bash
pnpm fmt:check && pnpm lint && pnpm typecheck && pnpm test
```

"It should work" is not verification. Neither is "the change is straightforward." If a command
wasn't run, say so. If a test fails, report it with the output rather than describing around it.

### Definition of Done

A task is complete only when **all** of these hold:

1. fmt, lint, typecheck and tests all pass — demonstrated, not asserted.
2. New logic has tests. Every invariant in §5 has a test that would fail without the guard.
3. `HANDOFF.md` reflects the current state.
4. `tasks/todo.md` has the item checked off.

## 8. Task & session tracking

| File | Purpose |
|---|---|
| `tasks/todo.md` | The plan as a checklist, written **before** implementing. Mark `[x]` as each item finishes — don't batch. |
| `tasks/lessons.md` | Chronological. After **any** correction or non-obvious discovery, append: what broke / root cause / what to do next time. |
| `tasks/agent_memory.md` | Durable structured reference: Architecture Decisions · Known Gotchas · Solved Problems · Useful Patterns. **Honour locked decisions even if the code suggests otherwise.** |
| `HANDOFF.md` | Written so a cold-start session can resume. Current State · Next Action (immediately actionable) · In-Flight files · Open Questions · Verification Baseline. |
| `docs/specs/` | Written specs (output of brainstorming). |
| `docs/plans/` | Implementation plans (output of writing-plans). |

**Update `HANDOFF.md` at every checkpoint:** task complete · milestone done · user signals stop ·
blocker hit · context ~70% · 30+ minutes since the last update.

### Start of every session

1. Read `HANDOFF.md`, `tasks/todo.md`, `tasks/lessons.md`, `tasks/agent_memory.md`.
2. Run `git status` and `git log -1`.
3. Reconcile. **If they diverge, the working tree is authoritative** — then fix `HANDOFF.md`.

## 9. Anti-patterns — do not do these

- A regex / keyword intent router doing the real routing. **Automatic fail.**
- A LangGraph-style node-per-command state machine. Explicitly called out as misreading the task.
- Business rules in the system prompt instead of in tools and the schema.
- Hardcoded clarifying questions instead of letting the model ask.
- Floating-point money.
- Read-modify-write on stock outside a transaction.
- Decrementing stock when an item is added to a bill rather than on finalize.
- Fake artifacts: a "PDF" that's text, a "deck" that's a screenshot, charts that are images.
- Claiming done without running the gate.
